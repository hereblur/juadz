Data Repositories

A data provider connects a resource to storage. Juadz calls only the operations implemented by the provider; those operations determine which standard routes are generated.

Knex provider​

@juadz/knex exports KnexProvider as both its default and named export. It receives a table name, a Zod object schema, and a Knex connection:

import KnexProvider from "@juadz/knex";
import knex from "knex";
import { z } from "zod";

const db = knex({
  client: "sqlite3",
  connection: { filename: "./app.sqlite3" },
  useNullAsDefault: true,
});

const userSchema = z.object({
  id: z.string().meta({ $create: false, $update: false }),
  name: z.string().min(1).meta({ $search: true, $filter: true, $sort: true }),
  email: z.email(),
});

const users = KnexProvider("users", userSchema, db);

The schema must match the columns and ID behavior of your database. Create your tables with Knex migrations before serving requests. Knex query filtering and sorting are restricted by the field flags described in Resource schemas.

MongoDB provider​

@juadz/mongo exports MongoProvider. It takes a collection name, schema, and connected MongoDB Db instance:

import { MongoProvider } from "@juadz/mongo";
import { z } from "zod";

const userSchema = z.object({
  id: z.string().meta({ $create: false, $update: false }),
  name: z.string().meta({ $search: true, $filter: true, $sort: true }),
});

const users = MongoProvider("users", userSchema, db);

Mongo documents use _id as the stored key; the provider exposes it as the resource id. Use valid MongoDB ObjectId strings for resource IDs. Mark other ObjectId-valued fields with $mongoId: true so query values are converted to ObjectIds:

ownerId: z.string().meta({ $mongoId: true, $filter: true }),

Provider contract​

A custom provider implements IDataRepositoryProvider<T> from @juadz/core:

import type { IDataRepositoryProvider } from "@juadz/core";

const users: IDataRepositoryProvider<User> = {
  name: "users",
  schema: userSchema,
  get: async (id) => findUser(id),
  create: async (data) => insertUser(data),
  update: async (id, patch) => updateUser(id, patch),
  replace: async (id, data) => replaceUser(id, data),
  delete: async (id) => deleteUser(id),
  list: async (query) => {
    const { data, total } = await queryUsers(query);
    return { data, total };
  },
};

All CRUD methods are optional. The provider must define name and schema. get, create, update, replace, and list return promises for records or query results; delete returns the number of deleted records. The list implementation is responsible for interpreting filter operators, sorting, and pagination in QueryListParam.

List query types​

A QueryListParam contains the resource name, normalized filters, an offset/limit range, and sort instructions:

{
  resource: "users",
  filter: [{ field: "name", op: "contains", value: "Ada" }],
  range: { offset: 0, limit: 20 },
  sort: [{ field: "name", direction: "ASC" }],
}

Providers return { data: User[], total: number }, where total is the number of matching records before pagination. The built-in adapters use field metadata to decide which fields may be searched, filtered, or sorted. Operator support depends on the selected adapter and database.

Providers should use parameterized query APIs for values and validate or allowlist identifiers. Do not interpolate untrusted request values into SQL or database operators. See routing and list adaptors for the default HTTP query syntax, or follow the custom provider implementation guide to build an adapter for your storage layer.
