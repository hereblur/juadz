Implement a Custom Data Provider

A provider is the storage adapter between a Resource<T> and your database or service. Implement IDataRepositoryProvider<T> from @juadz/core, then pass the provider to new Resource(provider). The provider must define name and schema; each CRUD method is optional. Only implemented methods generate their corresponding standard routes.

This example uses an in-memory map to demonstrate the contract. Replace the map operations with calls to your database or service.

Define the record and schema​

import { Resource, type IDataRepositoryProvider } from "@juadz/core";
import { z } from "zod";

const taskSchema = z.object({
  id: z.string().meta({ $create: false, $update: false }),
  title: z.string().min(1),
  done: z.boolean().default(false),
});

type Task = z.infer<typeof taskSchema>;

The schema must be a Zod object with an id field. Its types and metadata are used by resource validation and by adapters that inspect fields for search, filtering, and sorting.

Implement provider operations​

const records = new Map<string, Task>();
let nextId = 1;

const taskProvider: IDataRepositoryProvider<Task> = {
  name: "tasks",
  schema: taskSchema,

  get: async (id) => {
    const task = records.get(String(id));
    if (!task) throw new Error(`Task ${id} not found`);
    return task;
  },

  create: async (input) => {
    const task = {
      ...input,
      id: String(nextId++),
    } as Task;
    records.set(task.id, task);
    return task;
  },

  update: async (id, patch) => {
    const key = String(id);
    const current = records.get(key);
    if (!current) throw new Error(`Task ${id} not found`);

    const updated = { ...current, ...patch, id: key } as Task;
    records.set(key, updated);
    return updated;
  },

  replace: async (id, input) => {
    const key = String(id);
    const current = records.get(key);
    if (!current) throw new Error(`Task ${id} not found`);

    const replacement = { ...input, id: key } as Task;
    records.set(key, replacement);
    return replacement;
  },

  delete: async (id) => (records.delete(String(id)) ? 1 : 0),
};

export const taskResource = new Resource(taskProvider);

This provider exposes get, create, update, replace, and delete. It does not implement list, so the resource will not generate a list endpoint. Add list when the backend can implement its query contract.

The example throws a generic error for missing records. In a production adapter, decide how storage errors map to HTTP responses; a server integration can translate a not-found condition to the appropriate status. Avoid returning database driver errors or sensitive details to clients.

Implement list​

A list operation receives a normalized QueryListParam and returns a QueryListResults<T>:

import type {
  QueryListParam,
  QueryListResults,
} from "@juadz/core";

async function listTasks(
  query: QueryListParam,
): Promise<QueryListResults<Task>> {
  const allTasks = [...records.values()];

  // Implement every operator your API promises, or reject unsupported ones.
  const filtered = allTasks.filter((task) =>
    query.filter.every((filter) => {
      if (filter.field === "done" && filter.op === "=") {
        return task.done === filter.value;
      }
      if (filter.field === "title" && filter.op === "contains") {
        return task.title.includes(String(filter.value));
      }
      return false;
    }),
  );

  const total = filtered.length;
  const page = filtered.slice(
    query.range.offset,
    query.range.offset + query.range.limit,
  );

  return { data: page, total };
}

Add list: listTasks to the provider to enable GET /tasks. A complete adapter should also validate sort fields and directions, implement the operators it accepts, and calculate total before pagination. The built-in Knex and Mongo adapters use $filter, $sort, and $search schema metadata to constrain queryable fields; a custom provider should apply equivalent allowlists rather than trusting client-supplied field names.

Contract checklist​

  • Return the created, updated, or replaced record from write operations; resources use these results for their responses.
  • Apply update patches without replacing fields that are absent from the patch.
  • Keep ID handling consistent across provider methods and the schema's id type.
  • Return a delete count from delete.
  • For list, return { data, total }, where total counts matches before pagination.
  • Parameterize values and allowlist identifiers when building database queries.

For the HTTP-side adapter contract, see Use Juadz with another server.
